# Worked example — 2025.18.0 / 3.1.33

A complete real release, from Jira scope to published page. Use it as the calibration
reference: 23 tickets became 16 bullets in 5 categories, 3 were deliberately excluded, and
1 was lost — which is the most instructive part.

Published pages:

- <https://doc.nuxeo.com/nxdoc/web-ui-release-notes-2025-18-0/> — `2025` branch,
  `web-ui-release-notes-2025-18-0.md`, `tree_item_index: 983`
- <https://doc.nuxeo.com/nxdoc/web-ui-release-notes-3-1-33/> — `2023` branch,
  `web-ui-release-notes-3-1-33.md`, `tree_item_index: 968`

The two page bodies are **identical in content apart from the heading line** (`for LTS 2025
(Version 2025.18.0)` vs `for LTS 2023 (Version 3.1.33)`). That is the standard, not a
coincidence. Measured 2026-09-18, this published pair also differs by one blank line's
placement — content parity is the rule, and `lint-page.sh` compares with `diff -B` so harmless
whitespace drift between the branches is not treated as a defect.

Scope query:

```
project in (WEBUI, ELEMENTS) AND fixVersion = "2025.18.0" ORDER BY project, key
```

### The one that got away

| Ticket | What happened |
|---|---|
| `WEBUI-2180` — Web UI fails to load when an installed addon's dynamic chunk 404s due to a stale entry bundle (`nuxeo-platform-3d`) | **Not in the published notes, and not deliberately excluded.** |

This ticket carried `fixVersion 2025.18.0` and is a genuinely customer-visible failure — the
application not loading at all for a customer with the 3D addon installed. It was the **only
one of the 23 tickets with an empty Release Notes Summary field**, and the only one absent from
the page. The two facts are almost certainly the same fact.

The lesson, and the reason Step 3 exists at all: **the notes are assembled from the Release
Notes Summary fields, so a ticket with an empty field is invisible.** No one decided to omit it.
It simply was not there to copy.

So when you hit an empty field, do one of exactly two things — never leave a third state:

1. **Write the summary yourself** from the ticket, its comments and its PR (Mode A), fill the
   field, use it in the notes, and add the ticket to the "authored by the agent" list you hand
   back to the user at the end. `WEBUI-2180` would have been caught here: it needed nothing more
   than someone reading it.
2. **Exclude it with a stated reason** in the Step 6 ledger, if it genuinely has no
   customer-facing outcome.

An empty field is a process gap worth reporting — the person who delivered the ticket should have
filled it — but it is never a reason to ship incomplete notes.

## What the rewriting looks like

Engineer-written Release Notes Summary → published sentence:

> **`ELEMENTS-1951` field:** "The placeholder is now hidden/visible using the property which can
> be set in nuxeo.conf and the correct error message for invalid format."
>
> **Published:** "Administrators can now control the visibility of placeholders through a
> configurable nuxeo.conf property. The application also provides the correct validation
> message when an invalid format is used."

> **`WEBUI-2108` field:** "Fixed a TypeError in the \"recent documents\" feature caused by a
> corrupted/null local-storage value; navigation now works and self-heals the stored data."
>
> **Published:** "Fixed an issue where corrupted local storage data could prevent navigation
> from the Recent Documents list. The application now automatically recovers from invalid
> stored values."

Both rewrites do the same three things: name the actor ("Administrators", "The application"),
drop the implementation noun (`TypeError`, "local-storage value" → "local storage data"), and
split one dense clause into two clean sentences. The field is the engineer's raw material; the
page is the customer's sentence. Never paste the field through unedited.
